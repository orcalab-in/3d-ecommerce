# Design decisions

Every place a physical dimension or engineering trade-off was picked without an explicit spec value. Change the default in the relevant `products/*.py` `DEFAULTS`/`PARAM_SPEC` after test prints; update this file to match.

## Checkpoint 1 -- Photo lamp

- **Slot clearance: 0.4mm** (`slot_clearance_mm` default), carried over from the `lithophane.py` prototype's `stand_stl`. Loose enough for PLA warp tolerance on an A1 at 0.2mm layers without a visibly sloppy fit.
- **Stand slot geometry**: panel slot starts 12mm from the stand's front edge (`front_y` in `products/photo_lamp.py::_build_stand`); LED board slot follows after `stand_gap_mm` (default 10mm) diffuser gap. Both carried over from the prototype.
- **Caption embossing height: raised 0.6mm** (`caption_depth_mm` default), size 6mm em-square (`caption_size_mm`), font Open Sans. Centered on the stand's front lip, embedded 0.2mm into the stand body so the two independently-watertight solids fuse at the seam when printed (the same "embed slightly, don't just touch" trick used for the terrain/route joint in product 4 -- see below).
- **Rounded corner radius: default 0, max 20mm** (`corner_radius_mm`). Clamped to `min(radius, width/2, height/2)` in `mesh.corner_mask` so a radius request larger than the panel can't produce a degenerate/self-overlapping shape.
- **Font size semantics**: `size_mm` in `text.emboss_text` is the font's em-square height in mm, not cap-height or x-height -- a simple, easy-to-reason-about approximation rather than trying to read per-font metrics (OS/2 table cap-height etc.) for a small cosmetic feature.

## Checkpoint 2 -- Lithophane panel family

- **Hanging hole: 4mm diameter, 6mm margin from the top edge** (`hole_diameter_mm`/`hole_margin_mm` defaults on the `flat_hole` form). Fits a standard picture-hanging nail/hook without weakening the panel edge.
- **No CSG for the hole either.** `mesh.flat_panel_with_hole` masks out the grid cells under the hole's bounding box (after flattening that patch so the cut is coplanar), then bridges the resulting rectangular gap to a true circular loop via `bridge_loops` -- the same "stitch two loops, don't subtract volumes" approach as everywhere else in this package. `boundary_loops` (masking's outer perimeter + the hole's own perimeter) comes out CCW for the outer loop and CW for the hole automatically, by construction -- no separate classification step, same property already relied on for glyph holes in product 1.
- **Curved panel prints with the cylinder axis vertical.** Image X maps to arc angle, image Y to print height, and per-pixel thickness modulates *radius* -- purely in-plane at any given printed layer, so it can never create an overhang regardless of arc angle or radius (`mesh.radial_panel_grids`). This is why "arc 90-180 deg" from the spec needs no special-casing for printability: the same reasoning holds at any arc.
- **Full cylinder wrap (1-4 photos)**: each photo occupies `360/N` degrees, individually run through the same `load_heightmap` fitting logic, then resampled to a common row count and concatenated column-wise before the radial mapping -- reuses `radial_panel_grids` with `arc_deg=360, close_u=True`, no separate code path from the curved (open-arc) form.
- **Keychain: 40x50mm, thickness clamped to 0.4-2.0mm** regardless of what a caller passes for `min_thickness_mm`/`max_thickness_mm` (`resolve_params` clamps both), matching the spec's stated range exactly -- thinner keychains are too fragile at the hole, thicker ones don't read as a keychain. Border is capped at 2mm (vs the panel default 3mm) since a 3mm solid frame is disproportionate on a 40mm-wide part.
- **Bug found & fixed while building the rounded-corner panel in product 1, relevant here too**: `mesh.corner_mask` originally measured distance from the rectangle's actual corner *vertex*, which clips a single isolated far cell rather than a proper rounded bite (a correct rounded corner needs the arc's center inset by `r` from each edge, not centered on the vertex itself). Fixed before this checkpoint; flagged here because any future "cut a rounded/circular region from a grid" code should reuse `corner_mask`'s now-correct inset-center technique rather than re-deriving it.

## Checkpoint 3 -- Terrain map + Strava/GPX running line

- **Bounding-box margin: 12%** (`margin_frac`), footprint default **150x150mm, max 240mm** (`footprint_mm`/`max_footprint_mm`), vertical exaggeration default **1.5x** (`exaggeration`), minimum base thickness **4mm** (`min_base_thickness_mm`) -- all exactly the spec's stated defaults, made explicit parameters rather than baked-in constants.
- **Footprint letterbox rule**: `geo.fit_footprint` scales the route's (margined) bounding box so its *longer* side hits `footprint_mm`, preserving aspect ratio. An elongated point-to-point route prints as a non-square tile (e.g. 150x60mm) rather than being squashed to a square or cropped -- a squashed route would misrepresent the terrain's actual slope.
- **Terrain grid resolution: 1mm** (`terrain_res_mm`) -- fine enough for visible relief detail at up to a 240mm tile without the triangle count becoming a generation-time problem (a 240x240mm tile at 1mm is ~58k cells, well inside the 5s job budget).
- **Route ridge: 1.5mm wide, raised 1.2mm, embedded 0.2mm into the terrain** (`ridge_width_mm`/`ridge_height_mm`/`ridge_embed_mm`) -- the same "embed slightly rather than merely touch" fusion trick as the caption-on-stand decision in checkpoint 1, now applied to two independently-watertight solids of a *terrain-scale* size. Built via the new `mesh.ribbon` primitive, which treats a raised/inset line as `sweep_tube` with a 4-point rectangular cross-section instead of a circular one.
- **Inlaid channel: 0.8mm deep** (`channel_depth_mm`), falloff over the same `ridge_width_mm`/2 half-width via `geo.path_distance_field`, applied directly to the terrain heightmap (no second object) -- a single-color, hand-paintable alternative, as specified.
- **DEM network path avoids rasterio entirely**: OpenTopography is queried with `outputFormat=AAIGrid` (a trivial text grid), not GeoTIFF, so `dem.fetch_opentopo` + `read_aaigrid` need only numpy/stdlib `urllib`. Local GeoTIFF support (`dem.DemSource._read_local`) is the only place `rasterio` is used, and only if a `.tif`/`.tiff` is actually present in `dem/`.
- **Local tile takes priority over the network**: `DemSource.elevation_grid` checks `dem/*.hgt`/`*.tif` first and only calls OpenTopography if nothing local covers the route's bbox -- keeps routine regeneration (e.g. reprinting the same order) free and offline once a tile is cached once.
- **Start/finish markers are physical pins, not text labels.** The spec says "map-label engraving of start/finish markers" -- true text labels at that scale (a few mm) would be illegible when printed and complex to lay out without overlapping the route. Implemented instead as small embedded cylinders (`marker_radius_mm`=1.5, `marker_height_mm`=3, filament 2, same embed-for-fusion trick) at the route's first/last points. Revisit if a customer specifically wants text pins.
- **Bevel caption is a small text plate on the terrain's front (y=0) face**, not a literal carved bevel surface -- reuses the exact caption-on-stand technique from checkpoint 1 (`text.emboss_text` + the same (x,y,z)->(x,-z,y) rotation, embedded 0.2mm) rather than modifying the terrain mesh's edge geometry, which would need re-triangulating the front wall. Caption text is a single line (`"{name}  {distance}km  +{gain}m  {date}"`) at 2.5mm; very long activity names may overflow the tile width -- acceptable for now, not clamped/wrapped.

## Checkpoint 4 -- Paragliding flight terrain + track

- **Two track modes were both implemented, as the spec required, to make this trade-off explicit rather than assumed:**

  | | (a) tube + pillars | (b) plaque (**default**) |
  |---|---|---|
  | What it is | The track as a 3D swept tube, held up by thin vertical pillars down to the terrain every `pillar_spacing_mm` (default 15mm) | Track projected onto the terrain as a raised ridge (reusing product 4's ridge code) + a separate flat altitude-profile plate |
  | Printability | No supports needed, but pillar spacing/diameter has to be tuned to the specific flight's height-above-terrain profile -- a flight that stays very low for a long stretch needs closer pillars there or the tube sags/prints poorly in practice (not something this mesh-only validator can catch) | Printed flat on the bed; zero overhang risk at any point, for any flight, unconditionally |
  | Code reuse | New geometry: `mesh.sweep_tube` + per-span `mesh.cylinder` pillars | ~90% shared with product 4 (`mesh.ribbon` for the ridge) plus `text.extrude_polygon_2d` (already built for glyphs) for the plaque -- least new code of the two |
  | Print time / material | More (tube + N pillars, all raised well above the tile) | Less (thin ridge + a small flat plate) |
  | What it communicates | Literally 3D, visually dramatic -- shows the actual flight volume | More abstract (a 2D projection + a separate side-view profile), but unambiguous and robust |

  **Default: (b) plaque**, because it is safe to print unconditionally with no per-flight tuning, while (a) is offered via `--track-mode tube` for a more dramatic (but flight-profile-dependent) option. This mirrors the checkpoint-1 photo lamp/checkpoint-2 lithophane philosophy of the whole package: prefer the shape that's provably support-free over the shape that merely usually is.
- **Tube-mode altitude mapping uses AGL (height above the actual ground under the pilot), not raw altitude**, linearly mapped to `[pillar_min_height_mm=3, max_track_height_mm=70]` above the (already-exaggerated) printed terrain surface at each point. Raw GPS altitude would put the track at the wrong height relative to the terrain wherever the ground itself is high -- AGL is what actually varied during the flight and is what makes the print resemble "how high above the hill was the pilot," which raw altitude does not.
- **Pillars always at fixed spacing** (not conditional on height above terrain) -- matches the spec's literal "supported by thin vertical pillars every N mm down to the terrain" rather than a height-threshold heuristic, and is simpler.
- **Start/finish text labels became physical pins in product 4** ("markers"); the same reasoning applies to flight launch/landing, but paragliding landings are rarely at a named site (pilots land wherever there's a field), so `landing_site` commonly stays `None` -- the caption just omits it when absent (`"{launch}"` instead of `"{launch} -> {landing}"`), per the spec's own "if in the IGC header" qualifier.
- **Altitude plaque isn't slotted into the terrain.** The spec says it should "stand behind the tile," which a free-standing plate with its own flat, wide base (`plaque_base_mm`=4mm solid strip below the profile silhouette) satisfies without needing to cut a matching keyed slot into the terrain edge -- avoids a second hole-cutting operation for a feature whose main requirement (print flat, no overhang) doesn't need one. Mounting is by placement/glue, not a friction-fit joint; revisit if physical testing shows it needs to be secured more rigidly.
- **GPX input for this product must carry `<ele>` on its points** (checked explicitly, clear error if missing) -- an elevation-less GPX has no altitude profile to build a plaque or an AGL-based tube from, so failing fast with a clear message beats silently defaulting every altitude to 0.

## Engineering decisions that affect every product

- **No box-union CSG anywhere composite parts are needed.** The natural first instinct for a "floor + walls with gaps" shape (a stand, later a puck base, a backlit frame) is a union of touching `box()` calls -- this is what the prototype did, and slicers handle it fine visually, but it does NOT pass strict watertightness validation: a wall segment's footprint is a subset of the floor's footprint beneath it, so the touching faces are only *partially* coincident and can't be exactly cancelled. `mesh.slotted_base` instead builds these shapes as a single **stepped heightmap** (floor level everywhere, floor+height everywhere except the slot y-ranges) fed through the same `ruled_grid_solid` primitive used for lithophane panels -- genuinely one watertight solid, no seams. Each height step is encoded as a tight (`step_eps` = 0.001mm) pair of grid rows at the two levels so it reads as vertical rather than a ramp. Any later product needing a similar stepped/recessed shape (puck base, backlit box frame) should use this same technique, not box unions.
- **Grams/print-time reuse meshcheck's volume.** `api.generate` calls `meshcheck.check_mesh` once per object and reuses its `volume_mm3` for both the watertightness verdict and the weight/time estimate, instead of three separate full-mesh passes. On a laptop, `check_mesh`'s vertex/edge dedup is the dominant cost for a fine lithophane mesh (millions of triangles) -- worth avoiding running it twice. Vertex merging inside `check_mesh` also packs `(x,y,z)` into a single void-typed key before `np.unique` rather than using `axis=0` (which goes through a much slower generic multi-column lexsort); together these keep a full-size (150x200mm, res 0.2mm) photo lamp job around ~3s, under the 5s/job budget.
- **Text-embossing robustness has a per-glyph safety net.** Ear-clipping a polygon-with-holes (needed for any letter with a counter: b/d/o/p/q/e/g/B/... ) is a well-understood technique but a genuinely tricky one to get exactly right in floating point -- several real bugs were found and fixed building this (a duplicate bridge vertex, a bridge nudge landing on a meshcheck rounding boundary, two code paths silently re-deriving slightly different cleaned polygons). After those fixes, both bundled fonts render the full A-Z/a-z/0-9 set cleanly except a small handful of characters (~2-10 depending on font/backend) that still occasionally defeat the triangulator on specific glyph geometry. Rather than chase 100% coverage indefinitely, `text.emboss_text` validates every glyph's mesh before including it and **drops** (with a warning collected into `JobResult.warnings`) any glyph that can't be made watertight -- the cursor still advances correctly, so spacing is preserved and the rest of the caption is unaffected. A broken caption character is a much smaller problem than a broken print file.
